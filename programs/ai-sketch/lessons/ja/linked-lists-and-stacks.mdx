## 配列を超えて - 動的データ

データのサイズが事前にわかっている場合、配列は非常に便利です。しかし、一連のセンサー読み取り値、AI が処理するタスクのキュー、メッセージごとに増加する会話履歴など、データが予期せぬ形で到着した場合はどうなるでしょうか?滑らかに拡大および縮小する構造が必要です。

**リンク リスト**、**スタック**、**キュー**、つまり動的なトリオを入力します。

## リンクされたリスト - ノードとポインター

リンク リストには、項目が **ノード**のチェーンとして保存されます。各ノードは 2 つのものを保持します。データ自体と、チェーン内の次のノードへのポインター (参照) です。

```
[data: "A" | next: →] → [data: "B" | next: →] → [data: "C" | next: null]
```

配列とは異なり、リンク リスト ノードはメモリ内に並べて配置されません。それらはどこにでも散らばることができます。ポインターは単に次のものがどこにあるかを示すだけです。

<Illustration src="/images/lessons/linked-lists-and-stacks.svg" alt="3 つのノードが矢印で接続されたリンク リストと、連続したブロックを持つ配列との比較" caption="リンクされたリストのノードは、並んで配置される配列要素とは異なり、ポインターによって接続されます。" />

### リンクされたリストと配列

|操作 |配列 |リンクされたリスト |
|----------|----------|---------------|
|インデックスによるアクセス | O(1) ⚡ |お(ん)🐢 |
|先頭に挿入 |お(ん)🐢 | O(1) ⚡ |
|真ん中に挿入 |お(ん)🐢 | O(1)* ⚡ |
|途中から削除 |お(ん)🐢 | O(1)* ⚡ |
|メモリ使用量 |コンパクト |追加 (ポインタ) |

*一度位置を見つけても、それを見つけるのはまだ O(n) です。

### リンクされたリストが勝つ場合

- **頻繁な挿入と削除**: コレクションの途中でアイテムを頻繁に追加したり削除したりする場合、リンク リストを使用すると、配列に必要なコストのかかる移動を回避できます。
- **サイズが不明**: 保存するアイテムの数がわからない場合、リンク リストはサイズを変更することなく、一度に 1 ノードずつ拡大します。
- **他の構造の構築**: スタック、キュー、およびより複雑な構造は、リンク リストの上に構築されることがよくあります。

<ThinkAboutIt>ブラウザのタブ バーを使用すると、タブを自由に開いたり、閉じたり、並べ替えたりできます。開いているタブのリストを管理するには、配列とリンク リストのどちらが適していますか?途中でタブを閉じるとどうなるかを考えてみましょう。
</ThinkAboutIt>

## スタック - 後入れ先出し (LIFO)

**スタック**は、プレートのスタックとまったく同じように機能します。一番上に追加し、一番上から削除します。スタックに置かれた最後の項目が最初に取り出されます。

```
Push "A" → [A]
Push "B" → [A, B]
Push "C" → [A, B, C]
Pop      → [A, B]  (removed "C")
Pop      → [A]     (removed "B")
```

スタックを定義する 2 つの操作:
- **プッシュ**: 項目を上部に追加します。
- **ポップ**: アイテムを上から取り外します。

どちらも **O(1)** - スタック サイズに関係なく、瞬時に実行されます。

### 現実世界のスタック

- **元に戻す/やり直し**: すべてのテキスト エディタはアクションのスタックを維持します。 Ctrl+Z を押すと、最新のアクションがポップオフされ、元に戻ります。
- **ブラウザの戻るボタン**: 閲覧履歴はスタックされます。新しいページがそれぞれプッシュされます。 「戻る」をクリックすると、現在のページが表示されます。
- **呼び出しスタック**: コードが関数を呼び出すと、その関数は呼び出しスタックにプッシュされます。終わったら、外されます。これは、プログラムが自分の位置を追跡する方法です。

<FunFact>「スタック オーバーフロー」エラーが表示される場合は、文字通りコール スタックのスペースが不足していることを意味します。これは通常、関数が停止せずにそれ自体を呼び出し続けるためです (無限再帰)。有名な開発者 Q&A サイト Stack Overflow は、まさにこのエラーにちなんで名付けられました。
</FunFact>

### AI のスタック

- **式の評価**: AI コンパイラーとインタープリターはスタックを使用して、ニューラル ネットワーク計算グラフ内の数式を評価します。
- **バックトラッキング アルゴリズム**: AI が考えられる解決策を探索するとき (迷路を解くなど)、スタックを使用してそれがどこにあったかを記憶し、バックトラックできるようにします。
- **深さ優先検索**: ツリーとグラフを深さ優先で走査すると、当然スタックが使用されます。これについては次のレッスンで説明します。

## キュー - 先入れ先出し (FIFO)

**キュー** は、お店のキューと同じように機能します。最初に参加した人が最初にサービスを受けます。項目は後ろに追加され、前から削除されます。

```
Enqueue "A" → [A]
Enqueue "B" → [A, B]
Enqueue "C" → [A, B, C]
Dequeue     → [B, C]  (removed "A")
Dequeue     → [C]     (removed "B")
```

キューを定義する 2 つの操作:
- **エンキュー**: 項目を後ろに追加します。
- **デキュー**: 項目を前から削除します。

### 現実世界のキュー

- **印刷キュー**: ドキュメントは送信された順序で印刷されます。
- **タスクのスケジュール**: オペレーティング システムはキューを使用して、次にどのプロセスを実行するかを管理します。
- **メッセージ キュー**: Web アプリケーションはキュー (RabbitMQ や Kafka など) を使用して、何千ものリクエストをドロップせずに処理します。

### AI のキュー

- **幅優先検索 (BFS)**: レベルごとにグラフを探索するには、キューを使用します。これについては、ツリーとグラフのレッスンで説明します。
- **トレーニング データ パイプライン**: トレーニング データはキューにロードされるため、GPU は常に次のバッチを準備できるため、アイドル時間が防止されます。
- **リクエスト処理**: 数千人のユーザーが AI API に同時にクエリを実行すると、リクエストはキューに入り、順番に処理されます。

<Quiz question="AI API は 1 秒あたり 10,000 リクエストを受信します。リクエストが到着順に処理されることを保証する構造はどれですか?" options="スタック - 最新のリクエストを最初に処理します|ハッシュ マップ - 各リクエストを ID で検索します|キュー - 最初のリクエストが入力され、最初のリクエストが出力されます|配列 - すべてのリクエストを保存し、ランダムに処理します" answer="2" explanation="" />

<Callout>**優先キュー**もあり、アイテムは到着順ではなく優先順位に基づいてデキューされます。 AI systems use priority queues to process urgent tasks first - for example, a self-driving car might prioritise obstacle detection over route planning.
</Callout>

## AI の実際の使用: シーケンス処理とメモリ管理

### シーケンス処理

言語モデルはテキストをシーケンスとして処理します。 Under the hood, frameworks like PyTorch and TensorFlow use linked-list-like structures to build **computation graphs** - chains of operations where each step points to the next.

### ML フレームワークのメモリ管理

ニューラル ネットワークをトレーニングする場合、テンソル (多次元配列) が作成および破棄されるにつれて、メモリが常に割り当てられ、解放されます。メモリ アロケータは、多くの場合、空きメモリ ブロックのリンク リストを使用して、新しいテンソルに適したスペースを見つけます。

</ThinkAboutIt>

<FunFact>ほとんどのアプリケーションの取り消し履歴には制限があり、通常は 100 ～ 1,000 アクションです。この制限がないと、スタックは増え続けるメモリを消費することになります。一部の高度なシステムでは、スタックとキュー (「デキュー」) の組み合わせを使用して、最も古いアクションを破棄しながら最新のアクションを保持します。
</FunFact>

## 重要なポイント

- **リンク リスト** は、頻繁に挿入と削除が行われる動的データに優れていますが、インデックスへの直接アクセスが犠牲になります。
- **スタック** (LIFO) は、アンドゥ システム、バックトラッキング、および深さ優先トラバーサルを強化します。
- **キュー** (FIFO) は、タスクのスケジューリング、BFS、リクエスト処理における公正な順序付けを保証します。
- これらの構造は、多くの場合、AI フレームワークの舞台裏で動作し、メモリを管理し、シーケンスを処理します。
- Choosing between arrays and linked structures depends on your access patterns - random access favours arrays, dynamic modification favours linked lists.
