# 解码工作描述

每一份工作描述都是一份伪装成愿望清单的谈判文件。公司描述他们的**理想**候选人——一个符合所有条件的独角兽——然后雇佣那些符合**大多数**的人，并且面试得很好。如果您曾经因为未达到 100% 的要求而跳过招聘信息，那么您一直在错误地阅读 JD。本课程教您解读公司的实际需求和梦想。

## 60-70% 规则

惠普的内部研究（后来被 LinkedIn 推广）发现，男性在满足大约 60% 的资格时才会申请工作，而女性则倾向于等到满足 100% 的条件后才申请工作。现实情况是，**如果您满足所列要求的 60-70%，大多数公司都会面试您**。

为什么？因为：

- 职位描述由委员会撰写——招聘经理、招聘人员和人力资源部门都会添加项目
- 许多“要求”都是有抱负的，作为延伸目标添加
- 公司宁愿培训一名优秀的候选人来掌握其所缺少的技能，也不愿雇用一名能力较弱但在所有方面都符合的候选人

<Callout>如果职位描述与您的相似度达到 70%，请申请。如果感觉 50% 的人跟你一样，并且你真的对这个职位感到兴奋，那么无论如何都要申请并让招聘人员决定。自选是合格候选人错失机会的最常见原因。</Callout>

## 职位描述剖析

每个 JD 都有可预测的部分。以下是每一项的真正含义：

###“关于我们”部分
这告诉你公司的**叙述**——他们希望如何被感知。寻找：

- **阶段线索** — “快速增长”、“B 轮融资”、“既定领导者”标志着公司成熟度
- **使命语言** — 理想主义语言暗示了一种重视目标的文化
- **技术信号** — 提及特定工具或平台暗示堆栈

###“你会做什么”部分
这是JD最诚实的部分。它描述了**实际的日常工作**：

- 前 2-3 个要点是核心职责——这是工作的 80%
- 后面的要点是次要的或理想的
- 动词很重要：“build”意味着绿地； “维持”是指遗产； “领先”意味着管理层的期望

###“你需要什么”（要求）
这是大多数候选人被绊倒的地方。像这样解码它：

|京东语言 |它的真正含义是什么？
|----------|------------------------|
| “X+ 年经验” |粗略的资历信号，而不是硬性的截止|
| “React 专家” | React 中舒适的构建生产功能 |
| “分布式系统经验” |设计或开发过可水平扩展的系统 |
| “较强的沟通能力” |您将向非技术利益相关者进行演示 |
| “自启动” |最少的指导——团队可能资源不足|
| “快节奏的环境” |期限紧迫，优先顺序可能混乱 |

###“很高兴有”部分
这些是**真正的奖金**，而不是要求。拥有其中一两个可以让你的申请更有说服力，但缺乏所有这些并不会让你失去资格。

<FunFact>Textio 的一项研究分析了超过 5000 万份招聘信息，发现要求部分超过 15 个要点的 JD 收到的申请数量减少了 30% — 不是因为符合资格的人较少，而是因为长度吓倒了候选人不申请。</FunFact>

## 确定期望水平

JD 经常将资历信号隐藏在语言而不是头衔中。以下是解码级别的方法：

### 初级/入门级信号
- “渴望学习”、“提供指导”、“与团队一起成长”
- 提到0-2年的经验
- 专注于执行：“实现功能”、“编写测试”、“修复错误”
- 不太重视架构或领导力

### 中级信号
- “独立拥有的功能”，“跨团队协作”
- 3-5年经验
- 预计做出一些技术决策
- 可能会提到指导初级工程师

### 高级/员工信号
- “推动技术方向”、“影响架构”、“指导团队”
- 5-8年以上经验
- 预计进行系统设计和权衡讨论
- 跨团队影响、利益相关者管理

## 职位描述中的危险信号

并非每个职位发布都值得您花时间。注意这些警告信号：

- **“身兼多职”** — 可能意味着令人兴奋的广度，或者可能意味着他们想要一份薪水三个角色
- **“摇滚明星/忍者/大师”** — 不成熟的招聘文化；可能表明工程实践不佳
- **“努力工作，尽情玩耍”** — 经常长时间编码，偶尔举办披萨派对
- **职责模糊** - 如果你无法说出工作的实际内容，团队可能也不知道
- **不切实际的技术堆栈** - “React、Angular、Vue、Svelte、Python、Go、Rust 和 Kubernetes 专家” - 他们不知道自己需要什么
- **没有提及团队或经理** — 您将与谁一起工作？如果他们不说，就问。
- **频繁转发** — 如果同一职位已开放 6 个月以上，则可能存在保留问题

<ThinkAboutIt>查看您最近考虑申请的职位描述。您能确定哪些要求是真正必要的，哪些是理想的？了解 60-70% 规则后，您现在会申请吗？</ThinkAboutIt>

## 对 JD 面试进行逆向工程

JD 是您面试准备的备忘单。以下是如何使用它：

### 第 1 步：提取核心技术技能
突出显示提到的每项技术、框架和概念。这些将构成您的**技术准备清单**。

**JD 摘录示例**：“使用 Java 和 Spring Boot 构建可扩展的微服务。设计 RESTful API。使用 PostgreSQL 和 Redis。使用 Kubernetes 在 AWS 上部署。”

**您的准备清单**：Java、Spring Boot、REST API 设计、PostgreSQL 查询优化、Redis 缓存模式、AWS 服务 (ECS/EKS)、Kubernetes 基础知识。

### 第 2 步：确定系统设计主题
“您将做什么”部分暗示了您可能面临的系统设计问题：

- “构建可扩展的服务” → 期望：“设计一个每秒处理 10K 请求的服务”
-“实时数据处理”→期望：“设计实时分析管道”
-“支付系统”→期望：“设计具有幂等性的支付处理服务”

### 第 3 步：将行为问题映射到职责
每项责任都意味着一个行为问题：

-“领导一个由 5 名工程师组成的团队”→“告诉我一次你解决团队冲突的经历”
-“与产品和设计进行协作”→“您如何处理与非技术利益相关者的分歧？”
- “提高系统可靠性”→“描述您解决的生产事故”

### 步骤 4：研究差距
对于您缺乏的任何 JD 技能，请决定是否：

- **学到足够的知识来明智地讨论**（1-2天的学习）
- **准备一个诚实的答案**关于你将如何提升
- **跳过它**如果它显然是“很高兴拥有”

## 一个真实的解码示例

以下是“高级后端工程师”角色的简化 JD：

> **要求**：5年以上后端经验，强大的Java或Kotlin，微服务架构经验，熟悉云平台（AWS优先），了解CI/CD管道，优秀的沟通能力。

> **最好有**：具有事件驱动架构 (Kafka)、容器编排 (Kubernetes)、可观察性工具 (Datadog/Grafana) 的经验。

**解码**：

- **核心工作**：在 AWS 上构建和维护 Java/Kotlin 微服务。您将在一个频繁交付（提及 CI/CD）并跨团队沟通的团队中工作。
- **团队可能已经使用**：Kafka 用于异步消息传递，Kubernetes 用于部署，Datadog 或 Grafana 用于监控 - 他们只是不想吓跑使用替代方案的候选人。
- **面试准备重点**：Java 编码、微服务设计模式、AWS 服务、涉及事件驱动架构的系统设计问题以及 3-4 个有关跨团队协作的行为故事。

<Callout>为您申请的每项工作创建一个简单的电子表格：在一栏中列出 JD 所需的技能，在下一栏中列出您的证据/经验，在第三栏中列出您的准备计划。这将成为您针对每个应用程序的个性化学习指南。</Callout>

## 要点

- **以 60-70% 的匹配度申请** — JD 描述的是理想的候选人，而不是最低要求。
- **解码语言** - “自我启动”意味着自主，“快节奏”意味着紧迫的期限，多年的经验是指南而不是大门。
- **“你会做什么”部分是你最好的朋友** - 它揭示了实际的工作并提示面试问题。
- **注意危险信号** - 模糊的责任、不切实际的技术堆栈和“摇滚明星”语言都是警告信号。
- **对你的准备工作进行逆向工程** — 提取技能、预测系统设计问题并将行为故事映射到每个 JD。
